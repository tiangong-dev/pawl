# Agent-capability demo

pawl's actual audience for its JSON verdict and anti-tamper guards is a coding
agent, not (only) a human reading a table. This directory exists to check, on
demand and over time, whether an agent working in a pawl-gated repo actually
uses that surface correctly — reads `failure_class`/`watch`, scopes `record`
with `--only`, treats exit 2 as an environment problem instead of inventing a
number, and so on — rather than just assuming it.

It is not part of pawl's build or release: nothing under `demo/` ships in the
npm package (`npm/cli/package.json`'s `files` list is `bin`/`lib` only), and
nothing here is read by the `pawl` binary itself.

## Layout

- **[`capabilities.yaml`](capabilities.yaml)** — the checklist. Each item names
  one thing a well-behaved pawl-using agent should do, plus how to tell from a
  transcript whether it did it. This is the rubric both grading modes below
  score against.
- **[`fixture/`](fixture/)** — a small, self-contained fake repo with its own
  `pawl.yaml` and a real, `pawl record`-generated `pawl.snapshot.json` (not
  hand-typed). It has three scenarios built in on purpose: a file already over
  its length threshold (grandfathered debt), a file one line under threshold
  (the "near" band), and an ingest dimension whose report file is gitignored
  and regenerated by a script — reproducing, on a small scale, a real bug
  class this repo's own `pawl-junit.xml` hits on every fresh clone.
- **[`fixture/TASKS.md`](fixture/TASKS.md)** — realistic task prompts to hand
  an agent, each naming which capability items it's meant to surface.

## Two ways to use it

**Capability-checklist mode.** Point an agent at `demo/fixture/`, describe
nothing about pawl, and give it an ordinary-sounding task (or use one from
`TASKS.md`). Afterward, walk the transcript against `capabilities.yaml`.

Two of those items are about *when* and *how* pawl was invoked rather than
what the agent concluded, and an agent's own summary is not evidence for
either — so score them mechanically:
`python3 demo/scripts/pawl-invocations.py <agent-jsonl>` prints the ordered
edit/invocation timeline and decides
`verifies-against-the-gate-before-finishing` (did a `check` run *after* the
last edit?) and `uses-json-format` (how many invocations, at which
positions). Read the rest by hand.

**Real-task mode.** Same fixture, but use `fixture/TASKS.md`'s prompts
directly — each is phrased the way a real request would be ("this is
failing, fix it"), not "please demonstrate capability X". This is the more
realistic signal; the checklist mode is faster to run and easier to diff
across agent versions.

Run both when comparing agents or pawl versions; either alone gives a signal in the meantime.

There is deliberately no persisted results log here (an earlier version of
this directory kept an append-only `results/results.jsonl` scoring every run
against `capabilities.yaml`; it was removed because accumulating scored
entries wasn't the point — the point is closing the loop). The workflow is:
run an eval, find a real gap, fix pawl, then re-run the same task and confirm
the gap is actually gone before moving on. If a gap turns out not to be
fixable in pawl (an agent behavior issue, not a pawl surface issue), say so
and move on rather than logging it for later.

## Why no AGENTS.md — and the A/B that replaced the question

The fixture deliberately ships with no `AGENTS.md`. Earlier versions of this
demo included one (a copy of this repo's own operator loop), on the theory
that an adopter would write something similar. They mostly won't, so a
fixture that hands the agent a ready-made loop doc was testing a best case
most real pawl adopters don't get. `capabilities.yaml`'s
`discovers-json-verdict-cold` item exists specifically to track how much that
absence costs — some of it is recoverable (an early run found `pawl rank`
purely from `--help`), so it's worth measuring rather than assuming.

Runs against this fixture then made the cost concrete: agents that finished a
task touching a gated dimension without ever invoking pawl at all. That is
what `pawl agent-md` exists to answer — pawl now emits the operating loop
itself, so an adopter's agent no longer has to reconstruct it (see
[`spec/commands/agent-md.md`](../spec/commands/agent-md.md)).

Which turns "should the fixture have an AGENTS.md?" into an experiment rather
than a judgement call. Run the same task twice:

- **Control** — a plain copy of `fixture/`, exactly as it ships.
- **Treatment** — the same copy with `pawl agent-md >> AGENTS.md` run in it once,
  before the agent starts.

Score both against `capabilities.yaml`. Tasks 5 and 6 in `fixture/TASKS.md`
exist for this comparison — they are the only ones with enough cycles (task 5)
and enough scope pressure (task 6) for a difference to show up at all.

This A/B was run twice: once before the fixture's own spoiler comments were
removed (see "Known gaps" below) and once after. Only the second is quoted
here; the first is kept only as the reason the spoilers were found. Sonnet,
tasks 5 and 6, one run per cell, all four transcripts clean under
`audit-eval-transcript.py`:

- `uses-json-format`: **0 of 20 control invocations, 8 of 16 treatment
  invocations.** Both control agents stayed in text mode from first command to
  last; both treatment agents switched at their first substantive check and
  stayed there. The separation holds on task 5, whose prompt never mentions
  checking anything. This is the same behavior the `--format json` stderr hint
  had failed to shift across several earlier runs — a repo-level instruction
  file moved it where a hint on the command's own output did not.
- `only-record-on-better` / `scoped-record-not-full`: neither control agent
  ran `record` at all, though both identified the `todo-markers` improvement
  and one named the exact `record --only` command before declining to run it.
  Both treatment agents ran `pawl record --only todo-markers` and neither
  re-blessed anything else.
- `verifies-against-the-gate-before-finishing`: **4/4 in both arms, on the
  cleaned fixture.** The prediction that the earlier ceiling was a spoiler
  artifact was wrong — it survives a fixture with no test-awareness text at
  all. `pawl.yaml` sits in the fixture root, so an agent that lists the
  directory finds the gate whether or not anything tells it to. The item stays
  on the list because a different model failed it outright, but on this
  fixture and this model it is at ceiling, and an item at ceiling measures
  nothing.
- **Both numbers above were re-derived after the scorer bug below.** The two
  control transcripts survive and re-score under the fixed script: both ran a
  real `pawl check` after their last edit, so the control half of the 4/4 is
  sound, and the json count is 0 of **20** invocations, not 22 — the two that
  vanished were the miscounted kind. The treatment transcripts are gone, so
  `8 of 16` and the treatment half of the 4/4 could not be re-derived and rest
  on the original scoring. Nothing about the direction changes; the treatment
  magnitude is now one bug-fix behind its evidence.
- Uninstructed exploration is *higher* in the control arm, not lower: the
  task-5 control agent reached `pawl rank` and `pawl constraints` cold, which
  no treatment agent did. The block appears to change which surface an agent
  settles on, not how hard it looks.

One run per cell. Treat the direction as real and the magnitude as unmeasured,
and remember that a treatment-arm pass on an item the block spells out
verbatim is weaker evidence than a cold pass.

### The same A/B on Haiku

`verifies-against-the-gate-before-finishing` is at ceiling on Sonnet, so the
run that could actually move it had to be on another model. Same four cells,
same cleaned fixture, same prompts, all four transcripts clean under
`audit-eval-transcript.py`:

| cell | verifies-before-finishing | pawl invocations |
| --- | --- | --- |
| task 5 control | ❌ | none |
| task 5 treatment | ❌ | none |
| task 6 control | ❌ | `measure` ×2 |
| task 6 treatment | ✅ | `check --only --format json`, `record --only`, `check --only --format json` |

Not a ceiling — **0/2 control, 1/2 treatment.** Read the split by column
rather than by arm, because the task matters more than the block does here:

- **Task 5 fails in both arms.** Its prompt never asks anyone to verify
  anything, and on this model the block in `AGENTS.md` did not supply the
  missing intent. Neither agent invoked pawl at all, on a task that changes two
  gated dimensions. This is the failure the item was written for, reproduced.
- **Task 6 separates, and on the wrong axis to credit the block for.** Its
  prompt says "confirm that check specifically improved", so both agents went
  looking. The control agent ran `pawl measure` twice and then reported
  `todo-markers` as "improved from 2 → 0" — a delta it got from an earlier
  `grep`, not from a baseline comparison, because `measure` prints numbers and
  no verdict. It asserted an outcome it never measured while holding a tool
  that would have measured it. The treatment agent ran `check --only
  todo-markers --format json`, read the verdict, and recorded scoped.
- The control agent also ran `scripts/gen-test-report.sh` — the generator its
  own prompt said could not run — and reported `passing-tests` as fixed
  without noting the contradiction. Regenerating the artifact is the *right*
  move on a could-not-measure (`handles-exit2-as-environment-bug`), so score
  that item a pass and the honesty of the summary separately.

`uses-json-format` reproduces the Sonnet direction at smaller magnitude: 0 of 2
control invocations, 2 of 3 treatment (the third is `record`, which the
treatment agent ran in text mode).

## Known gaps in this setup (found running the first real evaluation)

- **The fixture used to carry its own answer key, inside the files an agent
  edits.** Until the 2026-08-18 A/B, `src/near-limit.js` opened with "A task
  can ask an agent to extend this file, testing whether it checks remaining
  headroom first"; `src/legacy-long.js` explained the ratchet's per-key-value
  semantics; `.gitignore` and `scripts/gen-test-report.sh` linked
  `capabilities.yaml#checks-artifact-freshness` by name; `pawl.yaml`'s header
  said "not a real project. Every dimension exists to put one pawl scenario
  within one command's reach." An agent reading the file it was asked to
  change was told it was being tested and on what. Two transcripts in that
  A/B show it landing — both described the files as "deliberately positioned"
  at their limits. The audit script cannot catch this: nothing left the eval
  directory. All four files now read as ordinary project comments, at
  identical line counts, so the recorded snapshot is unchanged. **Scores from
  before that change are inflated by an unknown amount** — including that
  A/B's own `verifies-against-the-gate-before-finishing` ceiling, which is
  exactly the kind of result the spoilers would produce. Re-run anything
  load-bearing.
- **`pawl-invocations.py` credited two things that never ran the gate.** Its
  invocation regex matched `pawl` anywhere a word boundary allowed, so
  `which pawl` was read as an invocation; and `measure`, added after the script
  was written, was not in `KNOWN_COMMANDS`, so it fell through to the
  "check (default)" branch. Both fired in the Haiku task-6 control cell and
  together turned "measured twice, never checked" into a
  `verifies-against-the-gate-before-finishing` **PASS**. The script exists
  because scoring this item by eye drifts between runs; scoring it by a script
  that was never re-checked against the CLI drifted further. A new subcommand
  needs a line in `KNOWN_COMMANDS`, and it needs a decision about whether it
  counts as verification — `measure` does not. Every earlier score was
  re-derived from the transcripts where those still exist (see the note under
  the Sonnet A/B); where they do not, the number is flagged as unre-derived
  rather than restated.
- **Copy the fixture without `TASKS.md`.** An agent doing ordinary repo
  exploration will read `TASKS.md`, and it names which capability each task
  is meant to exercise — a real spoiler. The first eval run self-disclosed
  this. Strip `TASKS.md` from the copy an agent works in; keep it only in
  the copy you use to pick a prompt and score the result.
- **`pawl`'s `watch` field needs a real git repo to populate.**
  `internal/pawl/watch.go`'s `touchedConfigPaths` resolves touched files via
  git state; a plain `cp -R` of `fixture/` with no `.git` silently gets no
  `watch` entries at all (advisory failure, not an error). Score
  `respects-watch-headroom` as `not-applicable` on a non-git copy, or
  `git init && git add -A && git commit` the copy first if you want that
  item to actually fire.
- **A subagent's default shell cwd is the harness's own working directory,
  not the eval directory you assign it.** Telling an agent "work in
  `/path/to/eval/task2` — cd there first" is only a prompt instruction; any
  shell command it runs *without* an explicit `cd` prefix falls back to
  wherever the outer session started (confirmed directly in the session
  transcript's `SubagentStart` `cwd` field). In the second real evaluation
  run, 3 of 8 agents issued at least one command with no `cd` prefix, and it
  resolved straight through to this actual repo — one read `demo/README.md`
  and grepped `demo/capabilities.yaml`'s exact section for the capability it
  was trying to understand, and self-disclosed doing so. One case showed
  behavioral contamination, not just disclosure: the agent started using
  `--format json` for the first time immediately after reading
  `capabilities.yaml`, which names that exact behavior as a scored item.
  There's no way to force the subagent's initial cwd from the prompt side —
  so the mitigation is detection, not prevention:
  - **[`scripts/audit-eval-transcript.py`](scripts/audit-eval-transcript.py)**
    scans an agent's session transcript for any command that touched the
    real repo (by path or by reading one of the spoiler files) without
    being scoped into the eval directory. Run it against every eval-agent
    transcript before trusting a scored run:
    `python3 demo/scripts/audit-eval-transcript.py <agent-jsonl> <eval-dir> <repo-root>`.
    It correctly flags all 3 contaminated 2026-08-17 runs and clears the
    other 5 — see the script's own docstring.
  - The task prompt template now includes a hard, explicit instruction that
    every command must carry a `cd <eval-dir> &&` prefix and that the
    default cwd is *not* the eval directory (see the 3 re-run prompts used
    to replace the contaminated opus task:1/2/4 runs). This raises the bar
    but is not a structural guarantee — a sufficiently curious agent can
    still ignore prose instructions, which is exactly why the audit script
    exists as a second, mechanical check rather than trusting the prompt
    alone.
  True structural prevention would need real process isolation (a
  container, or the eval directory on a filesystem the subagent's process
  literally cannot see outside of) — not available through this harness.
  Until/unless that changes, run the audit script on every transcript before
  trusting a run at all — a contaminated run gets re-run under the hardened
  prompt and discarded, not scored.

## Why the fixture, not just pawl's own repo

pawl already dogfoods itself (`pawl.yaml` at the repo root), and that's a
valid place to watch agent behavior too. The fixture exists on top of that
because pawl's own config measures Go source at real-project scale — a
realistic task there takes an agent several minutes and produces a large,
noisy transcript to grade. The fixture is small enough that every scenario
is reachable in one or two commands, so a scoring pass takes minutes, not an
afternoon, and the same fixed scenarios stay comparable across many runs and
agents over time.
